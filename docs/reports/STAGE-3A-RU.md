# Этап 3А: аккаунты, права и управление доступом

Дата: 16 ноября 2026. Изменения в ветке `ilker-management-stage1`.
Рабочий сайт и рабочая база не изменены. Это проверенный этап разработки, не готовность всей системы к публикации.

## Реализовано

- Отдельные аккаунты владельца и ресепшена. Владелец создаёт аккаунты, меняет имя, логин, роль и пароль, отключает доступ. Удаление аккаунтов не используется: история авторов сохраняется.
- Начальный логин владельца `owner`; первоначальный пароль наследуется из существующей конфигурации. Выдуманные Email не добавлены.
- При первом включении импортируются только хеш пароля, действующие сессии и привязки существующих Push-устройств. При перезапуске пароль из базы не заменяется старым значением окружения.
- Смена пароля через настройки с проверкой текущего пароля и длиной нового 12–200 символов. Scrypt с индивидуальной случайной солью; пароль не хранится в таблицах открытым текстом. Асинхронная проверка новых аккаунтов не блокирует цикл Node.
- Отзыв одной или всех собственных сессий; список устройств с укрупнённым типом браузера и временем активности. Полные User-Agent и IP в сессиях не сохраняются. Длительность сессии — 8 часов.
- Смена пароля, отключение сотрудника и смена роли отзывают его сессии и Push. Выход отзывает привязанные к сессии уведомления даже без endpoint в запросе.
- Важные изменения и операции с записями записываются с идентификатором реального сотрудника. Пароли, хеши паролей, токены, контакты и комментарии клиентов в журнал не попадают.
- Парольные операции требуют повторного ввода текущего пароля. В базе действует отдельный лимит ошибочных подтверждений. Вход ограничен по хешу логина и IP, лимиты общие между процессами; есть дополнительное ограничение HTTP-запросов.
- Права проверяются сервером по разрешённым маршрутам. Перед записью в БД действующая сессия и роль проверяются снова внутри транзакции — отзыв доступа во время запроса блокирует сохранение.
- Push-подписки принадлежат конкретным аккаунтам; чужое устройство нельзя перепривязать, протестировать или удалить через свой аккаунт.
- Настройки языка Push RU/AZ/EN и приватности сохранены в базе. Новые записи и тестовые уведомления локализованы; по умолчанию на экране блокировки скрыты даже дата и время. Контакты клиента не передаются в Push при обоих режимах.
- В админке появился раздел настроек: пароль, устройства, сотрудники, журнал действий и личные настройки Push. Недоступные ресепшену действия скрыты, а прямой вызов API блокируется.

## Матрица доступа

| Операция | Владелец | Ресепшен |
|---|---|---|
| Просмотр/создание/перенос записей, статусы и комментарии | Да | Да |
| Клиенты: поиск, создание, правка, история | Да | Да |
| Блокировка часов и исключения расписания | Да | Да |
| Цена конкретного визита в согласованном диапазоне, завершение | Да | Да |
| Финансовые отчёты и корректировки | Да | Нет |
| Архивирование визитов и обезличивание клиента | Да | Нет |
| Редактирование мастеров, комнат, каталога услуг | Да | Нет |
| Аккаунты сотрудников и аудит | Да | Нет |
| Собственный пароль, устройства и Push | Да | Да |

Индивидуальные цены и суммы посещений доступны ресепшену для работы с клиентами. Это не разграничение видимости отдельных клиентов между сотрудниками: ресепшен видит клиентскую базу салона. Автоматическая выгрузка всей базы отдельной функцией не предоставляется, списки постраничные и ограничены по частоте запросов. Разрешённый просмотр не может технически исключить ручное копирование.

## Проверки

См. `VALIDATION-STAGE-3A.md`. Проверены серверные запреты, CSRF, смена пароля, сохранение нового пароля после перезапуска, отзыв доступа во время операции, перенос старых сессий, привязка Push к аккаунтам, локализация/приватность уведомлений и ограничения попыток. PostgreSQL-проверки выполняются на отдельной тестовой ветке и в удаляемых синтетических схемах. Реальным клиентам сообщения не отправлялись.

## Инструкция владельцу (после проверенного выпуска)

1. Войдите с логином `owner` и прежним паролем. Откройте «Настройки».
2. Создайте сотруднику отдельный логин, роль «Ресепшен» и уникальный пароль. Не передавайте пароль владельца.
3. Для отключения сотрудника откройте «Настроить доступ» и снимите «Доступ разрешён». Сессии и Push этого аккаунта отзываются.
4. В «Ваши устройства» завершайте незнакомые сессии. При сомнении используйте «Выйти на всех устройствах», затем смените пароль.
5. После смены пароля войдите заново и включите Push на нужных устройствах. Язык и приватность сообщений настраиваются отдельно.

## Инструкция ресепшену

Используйте выданные владельцем логин и пароль. Работайте в «Главная», «Календарь», «Записи», «Клиенты» и «Расписание». В «Настройках» можно сменить собственный пароль и завершить свои сессии. Финансовую корректировку, правку каталога или обезличивание клиента выполняет владелец. При потере пароля свяжитесь с владельцем; автоматического Email-восстановления на этом этапе ещё нет.

## Ограничения и следующие этапы

- Полный перевод админки, восстановления пароля через Email, клиентские напоминания, персональные ссылки отмены, прочие события Push и межпроцессная аренда заданий ещё требуют реализации/проверки.
- Перевод интерфейса администратора пока частичный; публичные RU/AZ/EN сохранены. Смена языка панели обновляет язык Push текущего аккаунта; при ошибке сохранения отображается сообщение. Доставка на физический iPhone после этого изменения ещё не проверена.
- Реальный iPhone/PWA не проверялся: Chromium с мобильными размерами не является проверкой Safari или установленного приложения.
- Лимит входа может временно заблокировать логин при целевой атаке; нужен мониторинг перед выпуском. Успешные входы также учитываются, чтобы ограничить создание сессий.
- Нет заявления об абсолютной безопасности или завершённом аудите production. Независимая резервная копия Neon и репетиция восстановления ещё обязательны до выпуска.
- Для будущего Email-восстановления нужны подтверждённый адрес владельца и настроенный сервис отправки. Не добавлены фиктивные адреса и кнопки несуществующего восстановления.
- На бесплатном Render невозможно гарантировать точное выполнение фоновых задач во время сна сервера.
- Права на изменение пользователей защищены приложением; компрометация серверного секрета БД остаётся отдельным риском. Ограниченная роль не может переписывать аудит/финансовые проводки и читать таблицы прежнего бренда, что проверено отдельно.
- Отзыв подписки прекращает будущие отправки, но не может отозвать уже принятый Push-провайдером пакет.
- Откат на старый бинарный файл после смены пароля опасен: он может снова принять старый пароль окружения. План выпуска обязан сохранить новую авторизацию либо остановить доступ на время безопасного восстановления.

Проект ещё не готов к окончательной демонстрации как полностью завершённая коммерческая система. Для просмотра текущих функций можно использовать только изолированную тестовую среду с синтетическими данными.
