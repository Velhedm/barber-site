# Ruslan True: бронирование и PWA владельца

Node.js 24, Express, SQLite/WAL и стандартный Web Push (VAPID). Телефонная админка устанавливается на главный экран iPhone. Дизайн клиентского календаря и способ записи сохранены.

Рабочая версия находится в ветке `backend-booking`. Платные ресурсы не создавались, публичная статическая презентация в ветке `main` не заменялась серверным приложением.

## Локальный запуск

Требуется Node.js 24.x:

```bash
npm ci
cp .env.example .env
npm run admin:hash
npm run push:keys
```

Скопируйте хеш пароля и VAPID-ключи в `.env`. Сам пароль не записывайте в файл. `VAPID_SUBJECT` замените на свою контактную почту в формате `mailto:you@example.com` или HTTPS URL. Закрытый VAPID-ключ храните как секрет. Сохраните пару ключей между перезапусками и развертываниями: ее замена требует заново подписать устройства.

```bash
npm start
```

Клиент: http://localhost:3000/#slide-3
Владелец: http://localhost:3000/admin.html

На Windows можно скопировать `.env.example` в `.env` через Проводник. Локальные записи и файлы базы не включаются в Git. `.env` никогда не помещается в `dist/`.

## Настройки

| Переменная | Назначение |
|---|---|
| `PORT` | Порт сервера, по умолчанию 3000 |
| `APP_ORIGIN` | Точный адрес без завершающего `/` |
| `DB_PATH` | Локально `./data/bookings.sqlite`, на сервере `/data/bookings.sqlite` |
| `ADMIN_PASSWORD_HASH` | Результат `npm run admin:hash` |
| `VAPID_PUBLIC_KEY` | Открытый ключ Push, доступен вошедшему владельцу |
| `VAPID_PRIVATE_KEY` | Закрытый ключ Push, только на сервере |
| `VAPID_SUBJECT` | Контакт разработчика/владельца, `mailto:` или HTTPS |
| `NODE_ENV` | `production` для публичного запуска |
| `TRUST_PROXY` | `1` только за одним доверенным reverse proxy |

Для локальной работы без ключей бронирование и админка доступны, но Push выключен. Production требует origin, хеш пароля, VAPID-настройки и путь базы внутри постоянного `/data/`.

## Установка на iPhone

1. Разместите серверное приложение по **HTTPS** с постоянной базой. Внутренний `http://localhost` на компьютере подходит для разработки, но HTTP-адрес компьютера в Wi-Fi не заменяет HTTPS для iPhone.
2. На iPhone с **iOS 16.4 или новее** откройте `/admin.html` в Safari.
3. Нажмите «Поделиться» → «На экран Домой». В новых версиях iOS дополнительно включите открытие как веб-приложения, если этот переключатель предлагается.
4. Запустите админку с новой иконки и войдите с паролем владельца.
5. Нажмите «Включить Push» и разрешите уведомления. Запрос разрешения запускается только после нажатия.
6. Нажмите «Проверить Push». Затем сделайте контрольную клиентскую запись и проверьте уведомление.

`display: standalone` и Apple meta-теги открывают приложение без адресной строки браузера. Системные элементы iOS, например статус-бар и индикатор «Домой», управляются ОС. Учтены safe-area и поля ввода 16 px.

В обычной вкладке Safari на iPhone Push не запрашивается: интерфейс сначала предлагает установку. Если доступ запрещен, нужно разрешить уведомления в настройках устройства/браузера. На поддерживаемых Android/настольных браузерах возможна штатная установка через кнопку, если браузер выдаст `beforeinstallprompt`.

## Панель управления

- Защищенный вход с scrypt-хешем, HttpOnly/SameSite cookie и сессией на 8 часов.
- Все записи, включая прошлые, с обновлением каждые 3 секунды. Фильтры действующих/отмененных, поиск по имени/телефону, страницы по 50 записей.
- Календарь расписания: закрытие или открытие часа и всего дня.
- Закрытие дня запрещает новые записи, уже оформленные визиты остаются в списке.
- Отмена освобождает час. Чтобы полностью удалить персональные данные, сначала отмените запись, затем выберите «Удалить данные записи» в списке отмененных. Действия требуют отдельного подтверждения.
- Удаление отмененной записи удаляет связанные Push-задания каскадно. Уже показанное на устройстве уведомление не отзывается.
- Клиента об отмене мастер предупреждает отдельно. Автоматическая отправка клиенту не реализована.
- Выход отключает подписку текущего устройства на сервере и завершает сессию. Другие устройства владельца продолжают получать уведомления. При обычном истечении сессии Push-подписка сохраняется до отключения, а для просмотра деталей потребуется войти снова.

## Как работают Push

1. Вошедший владелец разрешает уведомления, браузер создает PushSubscription с `userVisibleOnly`.
2. Защищенный API сохраняет endpoint и ключи устройства в SQLite. Подписываться и удалять подписки можно только с сессией и CSRF-токеном. Разрешены известные Push-сервисы браузеров, произвольный серверный URL не принимается.
3. Клиентская запись атомарно сохраняет визит, событие Push и отдельное задание для каждого подписанного устройства. Нет устройства — запись все равно подтверждается, но Push-задание для него не создается.
4. Обработчик каждые 5 секунд передает уведомления Push-провайдерам. При временном сбое повторяет доставку с увеличением интервала до часа. Состояние очереди переживает перезапуск сервера.
5. Ответ 404/410 означает истекшую подписку: сервер удаляет ее и прекращает повторные запросы на этот endpoint.
6. Service Worker показывает уведомление. Нажатие открывает `/admin.html?booking=...`. Если сессия истекла, сначала будет вход, затем запись с выделением.

Текст уведомления содержит дату и час, **без имени и телефона**. Детали доступны только после входа в панель. На одно событие используется один `tag`, чтобы ОС могла объединять повтор. Успешный ответ Push-сервиса не доказывает показ уведомления или прочтение: доставка зависит от сети, разрешений, Focus/«Не беспокоить» и ОС. В случае неопределенного сетевого ответа возможна повторная передача.

Новые подписки получают только будущие события. Старые записи при подключении устройства не рассылаются. Лимит — 20 устройств владельца. Push не заменяет список записей и не влияет на успешность бронирования.

## PWA и офлайн

- `dist/manifest.json`: стабильный ID, start_url админки, standalone, цвета, иконки 192/512 и maskable.
- `dist/icons/apple-touch-icon.png`: иконка iPhone 180×180.
- `dist/sw.js`: Push, notificationclick, обновление кеша статической оболочки.
- `dist/offline.html`: безопасный экран без персональных данных при отсутствии сети.

**API, cookie, контакты и ответы с записями не кешируются.** Без интернета админка не делает локальных «успешных» изменений расписания. Нужно дождаться соединения и получить актуальное состояние сервера.

## Бронирование и данные

- Общая SQLite/WAL, один серверный экземпляр и постоянный файл.
- `BEGIN IMMEDIATE` и уникальный индекс запрещают две активные записи или блокировки на одну дату/час.
- Повтор запроса с тем же `requestKey` не создает повторную запись.
- Даты проверяет сервер по Баку (UTC+4), график 10:00–20:00, часовые старты 10:00…19:00, горизонт 365 дней.
- Клиенты получают обновления каждые 3 секунды. Если час заняли между выбором и отправкой, сервер возвращает 409 и предлагает другой слот.
- Сервер подтверждает запись сразу после транзакции базы. Доставка Push работает отдельно.
- Публичный API не возвращает имена/телефоны. Админские изменения защищены CSRF, Origin и ограничением частоты запросов.

При обновлении прежней серверной версии записи и сессии сохраняются. Старый неиспользуемый `outbox` удаляется миграцией, вместо него создаются `push_events`, `push_deliveries`, `push_subscriptions`. Секреты прежнего канала больше не читаются. Перед обновлением сделайте резервную копию SQLite.

## Основные API

| Метод | Маршрут | Назначение |
|---|---|---|
| GET | `/healthz` | Сервер и база |
| GET | `/api/meta` | Услуги, часы, время сервера |
| GET | `/api/availability?date=YYYY-MM-DD` | Публичная доступность |
| POST | `/api/bookings` | Запись с `name, phone, date, time, serviceId, requestKey` |
| POST | `/api/admin/login` | Пароль владельца |
| GET | `/api/admin/session` | Проверка сессии и CSRF |
| GET | `/api/admin/bookings?status=active&q=&offset=0` | Поиск/список всех записей |
| GET | `/api/admin/booking/:id` | Детали записи по уведомлению |
| GET | `/api/admin/day?date=...` | Расписание выбранного дня |
| POST | `/api/admin/slot` | `date, time, blocked` |
| POST | `/api/admin/day` | `date, closed` |
| POST | `/api/admin/cancel` | `id` активной записи |
| POST | `/api/admin/delete` | `id` отмененной записи |
| GET | `/api/admin/push/config` | Открытый VAPID-ключ, готовность, число устройств |
| POST | `/api/admin/push/subscribe` | `subscription` из PushManager |
| POST | `/api/admin/push/unsubscribe` | `endpoint` текущего устройства |
| POST | `/api/admin/push/test` | Тест на выбранную подписку |
| POST | `/api/admin/logout` | Выход, необязательный `endpoint` для отключения устройства |

Все `/api/admin/*`, кроме входа, требуют сессию. POST дополнительно требует `X-CSRF-Token`. Повторное подключение того же endpoint обновляет ключи, не создает дубликат устройства.

## Проверки

```bash
npm run check
npm test
```

Тесты используют реальную временную SQLite. Проверяются конкурентные заявки, идемпотентность, блокировки, отмена/удаление, перезапуск, права доступа, CSRF/Origin, регистрация подписок, рассылка на несколько устройств, повтор при сбое, 410, отключение и отсутствие контактов в Push. Сетевой Push-провайдер в автоматических тестах заменен тестовым обработчиком. Service Worker проверяется отдельно на безопасный переход и отсутствие кеширования API.

В браузере проверены мобильная сетка, список с polling, блокировки, отмена, удаление, offline-экран, выход, подписка/отписка и тестовое уведомление с имитацией PushManager. На физическом iPhone нужна контрольная установка и реальная доставка по HTTPS после настройки VAPID.

## Публикация позже

Текущий Static Site не исполняет Node.js и не может отправлять Push или хранить записи. Для этой реализации нужен один Web Service и постоянный диск. Бесплатная файловая система Render временная. Платные ресурсы не создавались.

Настройки Web Service из ветки `backend-booking`:

- Node.js 24.x.
- Build: `npm ci --omit=dev && npm run check`.
- Start: `npm start`.
- Health Check: `/healthz`.
- Постоянный диск `/data`, один экземпляр.
- `DB_PATH=/data/bookings.sqlite`, `NODE_ENV=production`, `TRUST_PROXY=1`.
- Точный HTTPS `APP_ORIGIN`, хеш владельца и стабильные VAPID-ключи.

При смене origin потребуется заново установить PWA/подписаться на новом адресе. Пока серверная версия не развернута по HTTPS, публичная презентация не становится рабочей админкой от одного добавления манифеста.

## Резервные копии

```bash
node --env-file-if-exists=.env scripts/backup.js /backup/new-file.sqlite
```

Команда `VACUUM INTO` создает согласованную копию. Родительская папка должна существовать, файл назначения должен быть новым. Храните защищенные копии вне сервера и проверьте восстановление. Копии содержат контакты и Push-подписки: ограничьте доступ. Не копируйте один `.sqlite` из работающей WAL-базы обычным `cp`.

Для масштабирования на несколько экземпляров перейдите на общую PostgreSQL и отдельную координацию очереди. С текущей SQLite и диском используйте один экземпляр.
