# Ruslan True: рабочее бронирование

Node.js 24 + Express 5 + SQLite (WAL). Внешний вид, календарь, часовые кнопки и последовательность формы сохранены. Клиентская имитация заменена API. Отдельная панель владельца доступна по `/admin.html`.

Эта версия подготовлена для локального запуска без платных ресурсов. Публичная презентация в ветке `main` остается прежней. Ветка с приложением: `backend-booking`. Ранее выданный адрес Render пока не является этим серверным приложением.

## Быстрый запуск

Требуется **Node.js 24.x** (Node 20 не содержит используемый `node:sqlite`). Откройте папку проекта:

```bash
npm ci
cp .env.example .env
npm run admin:hash
```

Введите собственный пароль владельца длиной от 12 символов. Утилита не показывает ввод. Полученную строку `ADMIN_PASSWORD_HASH=...` перенесите в `.env`. Сам пароль в файл не записывается.

В Windows вместо `cp` можно скопировать `.env.example` через Проводник и назвать копию `.env`.

```bash
npm start
```

Клиент: http://localhost:3000/#slide-3
Владелец: http://localhost:3000/admin.html

Токен Telegram необязателен для локальной проверки бронирования. Без него сообщения остаются в очереди, панель показывает отсутствие настройки. Для рабочей эксплуатации настройте Telegram до приема клиентов.

## Telegram

1. Создайте своего бота через официальный [@BotFather](https://t.me/BotFather), команда `/newbot`.
2. Укажите выданный токен в `.env`: `TELEGRAM_BOT_TOKEN=...`.
3. Откройте личный чат с созданным ботом от аккаунта владельца и отправьте `/start`.
4. Получите Chat ID:

```bash
node --env-file-if-exists=.env scripts/telegram-chat.js
```

5. Укажите `TELEGRAM_CHAT_ID=...` в `.env`, перезапустите сервер.
6. Сделайте контрольную запись на сайте и проверьте сообщение у владельца. Отмените контрольную запись в панели.

Утилита рассчитана на нового бота без webhook. Для существующего бота с webhook используйте известный Chat ID или получите его в своей интеграции. Не удаляйте чужую настройку webhook автоматически.

Все обращения к Bot API выполняет сервер. В браузер токен и Chat ID не попадают. Telegram получает имя, телефон, услугу, дату, интервал и идентификатор записи. Клиент видит согласие на передачу информации мастеру непосредственно перед отправкой.

## Настройки `.env`

| Переменная | Назначение |
|---|---|
| `PORT` | Порт сервера, по умолчанию 3000 |
| `APP_ORIGIN` | Точный адрес приложения без завершающего `/`, локально `http://localhost:3000` |
| `DB_PATH` | Файл базы, локально `./data/bookings.sqlite` |
| `ADMIN_PASSWORD_HASH` | Результат `npm run admin:hash` |
| `TELEGRAM_BOT_TOKEN` | Токен своего бота |
| `TELEGRAM_CHAT_ID` | Личный чат или группа владельца |
| `NODE_ENV` | Для публичного запуска `production` |
| `TRUST_PROXY` | `1` только при одном доверенном reverse proxy, например Render |

`.env` и база исключены из Git. Никогда не помещайте секреты в `dist/`.

## Что работает

- Сервер выдает актуальную занятость. Браузеры опрашивают API каждые 3 секунды, без перезагрузки страницы.
- Дата и время проверяются сервером по Баку (UTC+4). График сохранен: 10:00–20:00, старты 10:00…19:00, каждый визит занимает один час. Горизонт записи — 365 дней.
- SQLite-транзакция `BEGIN IMMEDIATE` проверяет закрытый день и слот, затем сохраняет запись и задание Telegram вместе.
- Уникальный индекс не допускает двух активных записей/блокировок на одну дату и час. Конфликт дает HTTP 409, клиенту предлагается выбрать другой час.
- `requestKey` обеспечивает идемпотентность повторной отправки с теми же данными. Повтор с тем же ключом возвращает существующую запись.
- После успешного commit клиент получает подтверждение базы. Ожидание Telegram не задерживает оформление.
- Очередь Telegram хранится в базе. Фоновая обработка идет каждые 10 секунд; при ошибке интервал повторов увеличивается до часа. Неотправленные задания переживают перезапуск.
- Доставка Telegram имеет семантику «как минимум один раз»: если Telegram принял сообщение, но ответ потерялся, при повторе возможен дубликат. Идентификатор записи в сообщении помогает его распознать. Это не повторная бронь.
- При отмене записи до обработки уведомления очередь ее пропускает. Уже отправленное или находящееся в отправке сообщение не отзывается.

## Панель владельца

Войдите на `/admin.html` с выбранным паролем.

- Нажмите на свободный час, чтобы закрыть его лично. Повторное нажатие открывает час.
- «Закрыть весь день» запрещает новые записи на дату. Уже подтвержденные визиты сохраняются, их нужно согласовать или отменить отдельно.
- «Открыть день» снимает блокировку дня, индивидуальные блокировки сохраняются.
- В записи клиента можно нажать «Отменить запись и освободить час». Потребуется отдельное подтверждение действия. Сам клиент уведомление об отмене автоматически не получает: свяжитесь с ним лично.
- Возле записи показано состояние Telegram: очередь, повторная попытка или отправлено.

Аутентификация: scrypt-хеш пароля, случайная сессия в HttpOnly/SameSite cookie, срок 8 часов. Сессии хранятся в SQLite. Мутации панели требуют CSRF-токен и проверяют Origin. Лимиты запросов ограничивают вход и публичную запись. Публичная доступность не раскрывает имена или телефоны клиентов.

## API

| Метод | Маршрут | Доступ |
|---|---|---|
| GET | `/healthz` | Проверка сервера и базы |
| GET | `/api/meta` | График, услуги, часовой пояс |
| GET | `/api/availability?date=YYYY-MM-DD` | Только состояния слотов |
| POST | `/api/bookings` | `name`, `phone`, `date`, `time`, `serviceId`, `requestKey` |
| POST | `/api/admin/login` | `password` |
| GET | `/api/admin/session` | Сессия владельца |
| GET | `/api/admin/day?date=YYYY-MM-DD` | Записи и доставка Telegram |
| POST | `/api/admin/slot` | `date`, `time`, `blocked` |
| POST | `/api/admin/day` | `date`, `closed` |
| POST | `/api/admin/cancel` | `id` записи |
| POST | `/api/admin/logout` | Завершение сессии |

Неавторизованные запросы панели дают 401, неверный CSRF/Origin — 403. Ошибка слота дает 409. Клиентские проверки дополняют серверные, не заменяют их.

## Проверки

```bash
npm run check
npm test
```

Интеграционные тесты используют настоящую SQLite во временной папке. Проверяются 20 конкурентных заявок на один слот, повтор запроса, блокировка часа/дня, отмена, перезапуск, отсутствие персональных данных в публичном API, авторизация, CSRF/Origin и повтор Telegram после имитированного сбоя. Реальные сообщения тесты не отправляют.

## Публичный запуск на Render позже

Текущий **Static Site** серверный Node-код не запускает. Не загружайте этот фронтенд поверх презентации отдельно: ему нужен API на том же origin.

Для этой реализации требуется **один Web Service и постоянный диск**. Бесплатная файловая система Render временная, поэтому для реальных записей непригодна. Платные ресурсы в рамках этой задачи не создавались.

В Dashboard создайте Web Service из ветки `backend-booking`:

- Runtime: Node, версия 24.x (задается `engines` в package.json).
- Build Command: `npm ci --omit=dev && npm run check`.
- Start Command: `npm start`.
- Health Check Path: `/healthz`.
- Постоянный диск: mount `/data`, небольшой объем, один экземпляр сервера.
- `DB_PATH=/data/bookings.sqlite`, `NODE_ENV=production`, `TRUST_PROXY=1`.
- `APP_ORIGIN=https://<адрес-нового-сервиса>` и секретные настройки владельца/Telegram.

При `NODE_ENV=production` приложение требует origin, корректный хеш пароля, Telegram-токен и Chat ID. Точка входа требует путь базы внутри `/data/`. Не используйте несколько серверных экземпляров с разными SQLite-файлами. С диском обновления могут сопровождаться краткой паузой. Для горизонтального масштабирования понадобится PostgreSQL и отдельная координация очереди.

До переноса старого домена проверьте новую ссылку, запись из двух браузеров, вход владельца, доставку Telegram и сохранность базы после перезапуска. Текущую презентацию можно оставить до завершения этих проверок.

## Резервные копии

```bash
node --env-file-if-exists=.env scripts/backup.js /backup/new-file.sqlite
```

Команда `VACUUM INTO` создает согласованную копию SQLite. Путь должен быть новым, родительская папка — существовать. Храните копии вне сервера с ограниченным доступом и проверьте восстановление на отдельной тестовой копии. Не копируйте только файл `.sqlite` из работающей WAL-базы обычным `cp`.

При восстановлении остановите сервер, замените базу согласованной копией и удалите старые соседние `-wal`/`-shm` только после остановки процесса. Резервные копии содержат персональные данные. Для Docker монтируйте постоянный том в `/data`. Для локальной разработки и одиночного сервера SQLite достаточно; надежность эксплуатации также зависит от резервного копирования и защиты аккаунта хостинга.
